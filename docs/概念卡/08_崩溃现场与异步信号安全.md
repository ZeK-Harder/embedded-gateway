# 概念卡 08 · 崩溃现场：信号处理骨架与 async-signal-safe

> 归属：crash 模块切片①（2026-10-29）。读法：先看「是什么」那一段的故事，再对照「我代码里的位置」，最后**合上卡**讲两句话。

## 1. 是什么

进程踩到一个没映射的地址（比如空指针）→ 内核发现"这块内存根本不存在" → 给这个进程发 **SIGSEGV（11 号信号）** → 默认动作是**当场杀死它，什么也不留**。你在终端上看到的 `Segmentation fault` 是 shell 替你报的，进程自己一个字都没写。

「崩溃现场记录器」做的事：**开机时就向内核登记"我出事的时候，先叫一下我这个函数"**（`sigaction`）。于是内核在杀进程之前，会先让 `on_crash` 跑一次。`on_crash` 只干两件事：

1. 往一个**早就打开好的文件**里 `write()` 一行：哪个信号、内核给的原因码、出错地址、哪个线程；
2. `_exit(128 + 信号号)` 自己退出（SIGSEGV → 139）。

这一行就是"尸检报告"。没有它，线上网关半夜挂掉，你只知道"没了"。

## 2. 为什么这么设计

- **为什么 fd 要在启动期打开（方案 A，你 2026-10-29 拍的）**：`open` 要查路径、查权限、跟文件系统打交道，每一步都可能失败。放启动期失败 = 程序起不来，你立刻知道；放崩溃那一刻失败 = 尸检报告没了，而那正好是你最需要它的时刻。代价是全程多占 1 个 fd。
- **为什么 handler 里只许 `write()`**：handler 是在"信号随时打断任何代码"的位置上被叫起来的 —— 被打断的那个线程可能正握着 stdio 的锁、正改着堆的内部结构。handler 里再调 `printf`（要拿 stdio 锁）或 `malloc`（要动堆）＝ **去抢一把可能永远没人放的锁**，结果进程既不退出也不打日志，就是"卡住"。`write` 是系统调用，不碰进程内这些锁。这张"允许清单"在 `man 7 signal-safety`，`printf` / `malloc` / `exit` / `snprintf` 都不在里面 —— 所以本模块的 `put_str` / `put_dec` / `put_hex` 全是手搓格式化。
- **为什么是 `_exit` 不是 `exit`**：`exit` 要跑 `atexit` 回调、要刷 stdio 缓冲，又回到上面那把锁上。`_exit` 直接进内核退出，什么都不跑。
- **为什么 `O_APPEND` + `O_CLOEXEC`**：追加写 = 多个线程同时崩时各自往后加、不互相覆盖；`CLOEXEC` = 常驻 fd 的代价要管住，不许漏给 exec 出来的子进程。
- **为什么 `SA_SIGINFO`**：登记成三参数版本 `on_crash(int sig, siginfo_t *si, void *uc)`，才拿得到 `si->si_code` / `si->si_addr`；不带它就只有信号号，等于没有尸检报告。

## 4. 易错点

1. **handler 里写 `printf`**：他打死也想不到的死法 —— 崩溃线程正握着 stdio 锁，handler 里 `printf` 再抢一次 → **进程卡住**（`timeout` 报 124），既没日志也不退出。同理 `malloc` / `free` / `snprintf` / `syslog`。
2. **忘了 `_exit`，或写成 `return`**：handler 返回后内核回到原指令再执行一次 → 再崩 → 再进 handler……**无限循环**，表现也是超时 124。这是本模块最容易漏的一行。
3. **`si_code` 当成非负整数打印**：SIGABRT 的 `si_code` 是 `SI_TKILL = -6`；用 `%u` / 无符号路径打出来会变成 `18446744073709551610` 这种天文数字。`put_dec` 里必须处理负号。
4. **`si_addr` 在 SIGABRT 上是垃圾值**：只有 SIGSEGV / SIGBUS 这个字段有意义。日志里照样打出来，但别拿它当真地址分析。
5. **`sa_flags` 忘了 `SA_SIGINFO`**：登记出去的是单参数 handler，内核却按三参数调（或者反过来）→ `si_code` / `si_addr` 全是垃圾，甚至当场再崩一次。
6. **`open` 不带 `O_CLOEXEC`**：网关将来 fork/exec 出来的子进程会继承这个 fd，且它指向一个"只该被崩溃写"的文件。
7. **一条记录拆成十几次 `write`**：两个线程同时崩，各自的片段会交错成两行乱码。`O_APPEND` 只保证"不覆盖"，**不保证整条记录原子**（真正的原子性要靠一次 `write` 写完 ≤ `PIPE_BUF`，或者自己加锁）。MVP 不处理，但这是已知边界。

## 5. 面试会怎么追问

- **"你在信号处理函数里调了什么？为什么？"** → 只调 `write` / `_exit` / `getpid`。因为 handler 跑在"进程半死"状态，`printf` 要 stdio 锁、`malloc` 要动堆，而崩溃线程可能正握着它们 → 会卡死而不是退出。清单在 `man 7 signal-safety`。
- **再追一层："`backtrace()` 在里面安全吗？"** → 严格说不安全：它可能 `malloc`、可能 `dlopen` 符号表，都不在安全清单里；工程上常用"记原始地址、事后 `addr2line` 还原"。这正是下一刀要权衡的事（要函数名方便 vs 严格安全）。
- **"为什么崩溃日志要预打开？"** → `open` 会失败（路径没了 / 没权限 / 盘满）。放启动期失败 = 起不来，立刻可见；放崩溃那一刻失败 = 日志没了。
- **"多线程同时崩怎么办？"** → `O_APPEND` 保证不互相覆盖，但一条记录是多次 `write`，会交错。要严格就得一次性 `write` 整条（限长）或加锁 —— V1 接受这个边界。
- **"为什么退出码是 139 不是 1？"** → `128 + 信号号` 是 shell 的惯例；`kill -9` 的 137、`abort` 的 134 都是同一套规则。运维看码就知道是信号杀死的。
