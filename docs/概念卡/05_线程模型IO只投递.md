## 概念卡 5：线程模型 —— IO 线程只投递，worker 干活，回投统一发

**是什么**：整台网关只有 **1 个 IO 线程**碰 socket（epoll 收字节、切帧、发送），另有 **N 个 worker 线程**只干业务（解码、以后落库）。两条边各用一条队列相连：IO → worker 是「帧任务」，worker → IO 是「要发的帧」，后者靠 `eventfd` 把睡在 `epoll_wait` 的 IO 线程叫醒。所以「谁碰 socket」和「谁干活」是两件被物理分开的事，一条帧要在两种线程之间走一个来回才发得出去。

**为什么**：业务是慢活（写 SQLite 一次几毫秒到几十毫秒），而 epoll 事件循环是**全服唯一的入口** —— 在里面做慢活，一条连接卡住，所有连接一起变慢。那为什么不干脆让 worker 自己 `send`？因为每条连接的 `wbuf / woff / wlen` 是共享状态：4 个 worker 同时往里追加，就会出现两个线程各写半帧，对端收到 10325 个坏帧那种画面（单线程时代的老账，多线程只会更频繁）。把发送收回到 IO 线程，写缓冲就**只有一个人碰**，一把锁都不用。剩下的问题是**顺序**：worker 并发处理后完成顺序是乱的，网关要求同一连接内响应保序，所以按「连接槽位号 % worker 数」分片 —— 同一条连接永远落在同一条队列、同一个 worker，FIFO 天然保序，不同连接仍然并行。

**我代码里的位置**：`src/pool/pool.{h,c}` —— `pool_start` 建 N 条 `task_queue` 再起 N 个 `worker_main`，`pool_submit(p, idx, t)` 投到 `p->w[idx % p->n].q`（idx 就是连接槽位，保序就靠这一句）。`src/net/epoll_server.c` —— 收齐一帧时 `malloc(struct frame_job)`（柔性数组 `buf[]` 带上帧字节副本 + `slot` + `gen`）→ `pool_submit`；worker 里 `frame_job_run` 做 `proto_decode` + 业务，成功后把同一个 `fj` 投回 `g_outq` 并 `write(g_efd, 1)`；IO 线程的 `drain_outq` 取出后调 `send_back` → `conn_queue` → 真正 `send`。验收证据：`verify/wsl-net-dispatch-check.py` —— 服务端打出 `io tid=137763562493760`，100 条 `frame` 行的 tid 是另外两个值（`137763546441280` / `137763554833984`），**与 io tid 互不相交**，且 2 条连接各 50 帧一个不丢；老脚本 `run-net-checks.sh` 6/6 PASS（`writebuf` 那条里 EPOLLOUT MOD 39 次、39484 帧全部可解码、seq 递增）。

**易错点**：① **不复制帧字节就投递**：`rbuf` / `frame_buf` 下一轮 `recv` 就被覆盖，worker 拿到的是别人刚写进去的字节 —— 表现是 CRC 随机失败、`seq` 跳号，而且压测跑得快时几乎必现、单帧手动测又看不出来。② **传 conn 指针而不是「槽位 + 代数」**：连接关掉后槽位会被新连接复用，旧任务手里的指针越界指向「同座位的下一位客人」—— 上一任的信寄给了下一任。我加了 `conn.gen`，`conn_alloc` 里 `gen += 1`，`send_back` 先校验 `used && gen == fj->gen`，不符就丢弃并打印 `drop: 连接已关闭 slot=N`。③ **`drain_outq` 先读 eventfd 再取队列**：worker 正好在两步之间 push + `write`，计数被这次 `read` 清掉，队列里有东西却没人再唤醒 —— 表现为偶发挂死（1000 次里挂 1 次那种）。正确顺序是「先取队列，再读 eventfd，读到就再来一轮」。④ **队列容量当装饰品**：一开始 `POOL_QUEUE_CAP=16384`，而 `writebuf` 验收一次灌 40000 帧，投递层就先丢帧了，EPOLLOUT 那条路根本压不到 —— 验收里 PASS1 直接红。调到 65536 才对。

**面试追问**：「为什么不用一条队列 + N 个 worker 抢？那样吞吐更高。」—— 因为抢式队列会让同一条连接的两帧被不同 worker 取走，完成顺序和投递顺序脱钩，回投之后发送顺序就乱了；网关要求同一连接内的响应保序，所以按连接分片。再追一层「分片的代价是什么」：热点连接只能吃一个 worker，单连接的处理上限就是单核；要突破就得在单连接内部也并行、再按序号重排，或者把业务改成完全无状态的流水线 —— 那是 V2 的事，现在这套的收益是「不用锁 + 天然保序」，代价写得进文档也就说得清。
