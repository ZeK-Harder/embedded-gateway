# V1 协议帧格式说明

> 适用范围：项目 A（epoll 工业网关 V1.0），设备经以太网 TCP 上报数据。
> 本文只定义帧层：怎么划边界、怎么检错、字段怎么摆。载荷内部语义不在本文范围（见第 9 节）。

## 1. 帧格式

线上字节顺序（"逻辑帧" = 转义前，"线上帧" = 转义后）：

| 字段 | 长度 | 含义 | 取值范围 |
| --- | --- | --- | --- |
| 帧头 | 1 B | 帧起始标记 | 固定 `0x7E` |
| LEN | 1 B | 本字段之后、到 CRC16 结束的逻辑字节数 | 6 ~ 255 |
| DEV_ID | 1 B | 设备 ID，标识数据来源 | 1 ~ 255 |
| FUNC | 1 B | 功能码，标识本条消息要做什么 | V1 仅 `0x01` |
| SEQ | 2 B | 序号，每帧递增，用于发现丢帧并定位丢的是哪条 | 0 ~ 65535，回绕 |
| PAYLOAD | 0 ~ 249 B | 数据载荷，帧层不解释其内容 | 任意二进制 |
| CRC16 | 2 B | 校验值，覆盖 LEN 至 PAYLOAD | 0 ~ 65535 |
| 帧尾 | 1 B | 帧结束标记 | 固定 `0x7E` |

- DEV_ID 取 1 字节：车间 30 台设备，1 字节最多 256 个地址，够用且留余量。
- 功能码 V1 只定义 `0x01` = 数据上报；其它取值视为非法帧，记录日志后丢弃，**不中断连接**。

## 2. LEN 的定义

- 起点：LEN 字段**自己的下一个字节**
- 终点：**CRC16 的最后一个字节**
- 帧尾 `0x7E` **不计入**

```
LEN = 1(DEV_ID) + 1(FUNC) + 2(SEQ) + payload_len + 2(CRC16)
    = 6 + payload_len
```

由此：`payload_len` 范围 0 ~ 249；`LEN` 范围 6 ~ 255。

LEN 记录的是**转义前**的逻辑字节数，不是线上字节数。理由见第 3 节末尾。

## 3. 转义规则

**转义范围**：两个 `0x7E` 之间的**所有**字节，含 LEN、DEV_ID、FUNC、SEQ、PAYLOAD、CRC16。
帧头帧尾不参与转义——它们在转义完成之后才被加上。

| 逻辑字节 | 线上字节 |
| --- | --- |
| `0x7E` | `0x7D 0x5E` |
| `0x7D` | `0x7D 0x5D` |
| 其它 | 原样 |

转义完成后必须成立的两条不变式：

1. `0x7E` 只出现在帧的头尾两处
2. `0x7D` 之后必然紧跟 `0x5E` 或 `0x5D`

**为什么必须转义**：

- 若解析器完全按 LEN 读帧，数据里出现 `0x7E` 并不影响这一帧的解析。但 LEN 读法有一个前提：解析器站在正确的起点上。
- 一旦起点错了（LEN 被干扰改坏、上一帧被截断、程序重启后接到半截字节），解析器必须重新对齐；而重新对齐唯一的办法是向后扫描下一个 `0x7E`。如果数据里存在未被转义的 `0x7E`，扫描会落在错误位置，错误从此一直延续。
- 所以转义的主要目的**不是**"让当前这一帧能被读懂"，而是让 `0x7E` 成为绝对可信的路标，赋予解析器**重新同步（resync）**的能力。
- `0x7D` 也必须转义：它是转义机制自己引入的提示符。若原样出现，反转义会把它后面的字节一并吃掉——`11 7D 41 22` 被还原成 `11 61 22`，4 字节变 3 字节，且不报错，属于静默篡改。

**LEN 与 CRC 均为转义前的值**：

转义会改变字节数，而某个字节是否需要转义又取决于它的值。若规定 LEN 记录转义后的字节数，LEN 的值就会参与决定 LEN 自己转义后占几个字节，发送端无法算出自洽的结果（例如 LEN = 126，转义为 `7D 5E` 后长度变成 127，而 127 不需要转义，长度又回到 126）。因此 LEN 与 CRC 只能定义在转义前这一侧：接收端先反转义，再查 LEN、算 CRC，全部工作在逻辑字节上进行。

## 4. 字节序

所有多字节字段一律**大端序**（高位字节在前）。

- SEQ、CRC16 按大端序发送
- 例：CRC16 = `0x4B37`，线上顺序为 `4B 37`

注意：Modbus RTU 的 CRC 是**低字节在前**，与本协议相反。以后实现 Modbus 时不能凭习惯照搬。

## 5. CRC16 参数

| 项 | 值 |
| --- | --- |
| 算法 | CRC-16/MODBUS |
| 多项式 | `0x8005`（反射实现用 `0xA001`） |
| 初值 | `0xFFFF` |
| 输入反转 | 是 |
| 输出反转 | 是 |
| 结果异或 | `0x0000` |
| 覆盖范围 | LEN 至 PAYLOAD 的最后一个字节（转义前的逻辑字节） |
| 校验值 | `"123456789"` → `0x4B37` |
| 空数据 | `0xFFFF`（等于初值） |

## 6. 帧长上限与解析约束

| 量 | 上限 | 算法 |
| --- | --- | --- |
| 逻辑帧 | 256 B | 1（LEN 自身）+ 255 |
| 线上帧 | 514 B | 256 × 2（最坏情况每个字节都被转义）+ 2（帧头帧尾） |
| 接收缓冲上限 | 514 B | 累计到 514 B 仍未见帧尾 → 判超长帧，丢弃并重新同步 |

严格计算：LEN = 255 时其自身为 `0xFF`、无需转义，理论最大为 513 B。缓冲上界取 514 更安全——多一个字节没有代价，少一个字节会漏掉最坏情况。

其它解析约束：

- 反转义后实际字节数与 LEN 不符 → 判破帧，丢弃
- 相邻两帧首尾相接时会出现连续两个 `0x7E`，两标记之间为空 → 丢弃空帧，继续扫描（待实现时验证）

## 7. 收发流水线

**发送**：

1. 算 `LEN = 6 + payload_len`
2. 算 CRC16（覆盖 LEN 至 PAYLOAD，逻辑字节）
3. 转义（LEN 至 CRC16 的全部字节）
4. 两端加 `0x7E`

**接收**：

1. 扫描寻找帧边界（`0x7E ... 0x7E`）
2. 反转义
3. 查 LEN 与实际字节数是否一致
4. 算 CRC16 并比对
5. 通过 → 交上层；失败 → 丢弃并记日志

## 8. 示例报文

以下字节均由 `src/proto/codec.c` 的 `proto_encode` 实际输出，与实现保持一致。

**示例 1**：DEV_ID=`0x11`，FUNC=`0x01`，SEQ=`0x0001`，PAYLOAD=`01 02 03`

```
7e 09 11 01 00 01 01 02 03 ec 91 7e
```

| 字节 | 含义 |
| --- | --- |
| `7e` | 帧头 |
| `09` | LEN = 6 + 3 = 9 |
| `11` | DEV_ID |
| `01` | FUNC |
| `00 01` | SEQ（大端） |
| `01 02 03` | PAYLOAD |
| `ec 91` | CRC16（大端） |
| `7e` | 帧尾 |

共 12 字节：逻辑帧 10 字节（无字节需要转义）+ 2 个帧界标记。

**示例 2**：DEV_ID=`0x22`，FUNC=`0x01`，SEQ=`0x0102`，PAYLOAD=`7e 7d ff`

```
7e 09 22 01 01 02 7d 5e 7d 5d ff c2 be 7e
```

逻辑帧为 `09 22 01 01 02 7e 7d ff c2 be`（10 字节），其中 `7e` 与 `7d` 各被转义为一个双字节序列，因此线上为 12 字节，加帧界后共 14 字节。

**示例 3**：DEV_ID=`0x33`，FUNC=`0x01`，SEQ=`0xffff`，PAYLOAD 为空

```
7e 06 33 01 ff ff 34 f3 7e
```

LEN = 6 + 0 = 6；逻辑帧 7 字节，线上共 9 字节。
